# コメントは「Why」を記録する（Comments Explain Why）

ソースコード内のコメントは、非構造化された自然言語であり、コンパイラによる静的検証やリファクタリングツールの自動追従が機能しない。
実装変更に伴いコメントは容易に陳腐化し、誤読を誘発するノイズとなる。

したがって、すべてのコメントは潜在的な保守負債として管理する。
コメントの記述は最小限に限定し、型、命名、制御構造、テストコード、設定ファイルでは表現できない「意思決定の理由（Why）」の記録にのみ用いる。

## 表現手段と責務分担

| 表現手段 | 担う責務 | 答えるべき問い |
| :--- | :--- | :--- |
| **Docstring（仕様定義）** | 呼び出し側に公開される外部契約 | この抽象は何を提供するのか？（What） |
| **実装コード（Implementation）** | 実行される具体的な仕組みや手続き | どのように実現しているのか？（How） |
| **コメント（Comment）** | コード自体からは復元できない判断理由 | **なぜこの選択が必要だったのか？（Why）** |

Docstring は外部契約（What）を定義する場所であり、実装コードの解説ではない。
実装コード自体が、適切な命名、型定義、境界分離、制御構造により、その実現手段（How）を自己言及的に示さなければならない。
コメントは、成立可能な複数の選択肢から特定の手法を選択した「意思決定の根拠（Why）」を永続化するためにのみ用いる。

## コメントが記録すべき対象

有効なコメントは、コードから直接復元できない以下の文脈を保存する。

* 非自明な実装を強制した、外部システムやライブラリの制約
* 一見して自然に見える代替案を採用できなかった論理的理由
* コード表面に表れないトレードオフおよび性能上の制約
* 変更時や削除時に破壊される危険性のある不変条件への警告

コメントは、将来の保守者が「前提制約が現在も有効か」を客観的に再評価できる十分な文脈を含まなければならない。
単に使用技術を言い換えるだけの記述を排する。

## コメントによる代替を禁じる事項

コードの動作説明、型定義の復唱、制御フローの逐語解説、可読性の低い実装の釈明としてコメントを用いてはならない。
意図が自明でないコードに対しては、コメントの追加ではなく、データモデル、識別子の命名、関数分割、制御構造自体のリファクタリングにより対処する。
