# デフォルトでの不変性（Immutability by Default）

データおよび値は、原則として**不変（Immutable）**として設計しなければならない。
状態変更は、既存オブジェクトのインプレース書き換えではなく、「現行値から新値を導出する純粋な変換」として表現する。

## 破壊的変更（Mutation）に伴うリスク

破壊的変更（Mutation）はデータへ時間的依存性を導入する。
同一オブジェクトの参照がタイミングに応じて異なる値を保持することにより、プログラムの正当性が「実行順序」「参照エイリアス」「競合書き込み」などの暗黙の前提に依存する。
これは時間的結合（Temporal Coupling）を誘発し、コードの局所的な論理推論を破綻させる。

不変性を維持することにより、値は生成後に固定化される。
呼び出し側は競合調整なしに安全にデータを共有でき、関数は入力のみに基づく決定論的な結果を保証する。
検証完了後の値の改ざんが排除されるため、静的型システムによる制約保護も担保される。

## 設計ルール

ドメインモデル、関数の入出力、コレクション、設定値は、すべて不変データとして設計する。
状態遷移は「値 A から値 B への明示的変換」としてモデル化し、責務境界で可視化する。

言語が提供する読み取り専用修飾子および不変データ構造を活用し、プロパティやコレクションへの意図しない書き込みをコンパイル時に阻止する。

## 例外としての可変性

ステートフルな外部通信プロトコルとの連携や、[実測により証明された致命的な性能ボトルネック](../approach/optimize-last-by-evidence.md)など、特定要件を満たすための破壊的変更は例外として許容される。
ただし、実装の利便性のみを根拠とした可変性の導入は禁じる。

可変性の導入が避けられない場合、以下の規律を遵守しなければならない。

* 破壊的変更を不可逆的に要求する技術要件の特定
* 変更スコープの最小コンポーネント内および短寿命ライフタイム内への局所化
* 境界を越えるミュータブル参照の外部漏洩の阻止
* 許可された状態遷移および保護すべき不変条件の明示
* [可変性が必要となった根拠（Why）](comments-explain-why.md) のコメント記録

不変性はデフォルトの前提であり、可変性（Mutability）の導入には厳格な妥当性の証明が要求される。
