# 設計としての型システム（Types as Design）

型システムは、コードへの事後的な注釈（アノテーション）付与手段ではなく、**設計を記述するための表現媒体**である。
優れた設計は、実装ロジックの記述に先立ち、ドメインの概念、有効な状態、許可された遷移、所有権、責務境界の契約を型として定義する。

型システムの目的は、**設計に反するコードのコンパイル通過を構造的に阻止すること**にある。
不正状態を表現不能（Unrepresentable）とし、不正操作を呼出不能とすることで、実行時テストに先立ち重大な欠陥クラスを構造的に排除する。

## 証明責務としての型

型システムにおける型とは取り得る値の集合であり、型間の関係性は許可される値と操作を規定する。
コンパイラはプログラム全体にわたり関係性を静的に検証し、制約を満たさないコードを拒絶する。

型検査の成功とは、「コードが静的制約を満たしていることの機械的証明」を意味する。
その証明の有効性はモデルの厳密性に依存する。
過度に広い型定義、無検証のアサーション、未検証の外部入力は、不正値の混入を許容し、静的証明の効力を減殺する。

実行時の内部表現が類似している場合であっても、ドメイン概念を型レベルで厳格に区別し、状態遷移を型検査により網羅的（Exhaustive）に制御する。

## ロジックに先立つ型の確定

実装プロセスは、要件および不変条件を型定義へ翻訳することから開始する。
これにより、処理コードの記述に先立ち、未考慮の状態、曖昧な所有関係、不正な状態遷移が静的に抽出される。

エンジニアリングの責務は、「正当な実装のみが許容され、設計規約違反がコンパイルエラーとして拒絶されるモデル」の構築にある。
確立されたモデル上での実行時ロジック記述は、設計の表現ではなくモデルの具現化に該当する。

## テストとの役割分担

外部入力、アルゴリズムの正当性、統合境界、実行時性能など、コンパイラが静的に検証できない領域は、テストによって検証する。
外部データは、信頼されたドメイン型へ変換する前に実行時バリデーションを経なければならない。

ただし、テストを不完全な型モデルの補填手段として用いてはならない。
型定義により設計違反のコンパイルを阻止した上で、型では表現不能な動的振る舞いをテストで検証する。

これは [唯一の事実源（Single Source of Truth）](../system-design/single-source-of-truth.md) の原則に合致する。
静的表現が可能な不変条件に対しては型モデルが権威ある定義であり、コンパイラがその強制機構を担う。
型システムが直接保証する制約を、テストコードで重複検証することを排する。
