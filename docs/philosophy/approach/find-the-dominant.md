# 成否を決定づける支配的要因を見極める（Find the Dominant）

ソフトウェア開発で成果の価値を決定づけるのは、投入された努力の総量ではなく**システムの構造**である。

アーキテクチャの構造自体に誤りがある場合、個々の実装を精緻に記述しても全体としての価値は生まれない。
逆に、責務境界が正しく整理された構造であれば、簡潔な実装であっても安定して高い成果を維持できる。

## 単一の支配的要因への集中

あらゆる開発課題には、その成否を最終的に左右する**決定的な要因（支配的要因）**が存在する。

支配的要因を見誤ったまま周辺コードを精緻化しても、破綻を回避することはできない。
課題の着手時に特定すべき問いは、「成否を決定づける支配的要因は何か」である。
支配的要因を特定した上でリソースを集中させ、副次的な要素は必要十分な水準で最小限に整える。

課題の性質に応じた支配的要因の典型例を以下に示す。

* **外部システム連携**：外部プロトコルの挙動、切断時の振る舞い、レート制限が支配的要因となる。
  内部処理の最適化に先立ち、外部連携の境界挙動を検証する。
* **大規模データ基盤**：高負荷下におけるスループットと書き込み耐性が支配的要因となる。
  ロジックの局所的最適化よりも、計測による I/O ボトルネックの特定を最優先とし、その解消は [計測に基づく最終手段](optimize-last-by-evidence.md) の順序に従う。
* **複数コンポーネントの協調**：コンポーネント間の明示的な契約定義が支配的要因となる。
  契約が曖昧な状態での個別実装は、後の全面的な再設計を招く。

副次的な機能を精緻化しても、支配的要因が破綻すればシステムは成立しない。
設計における責務は、この支配的要因を特定し、設計と実装のリソースを傾注することにある。

## 表面的な症状ではなく構造を直す

同一の不具合や障害が反復する場合、確認手順の増加や作業者の注意力に依存した解決を図ってはならない。
構造的欠陥を放置したまま人的運用を強化しても、問題の再発は防げない。

継続的な問題発生に対しては、対症療法的な個別修正に先立ち、背後にある構造的要因を分析する。

* 局所的な変更が広範囲の破壊を招く場合、原因は注意力の欠如ではなく**凝集性の不足および不適切な責務境界**にある。
* 変更適用時のデータ欠損への懸念は、運用手順の問題ではなく**不変ログの永続化および自律的な再開構造の欠如**に起因する。

反復する失敗に対しては、人的規律に依存せず、**構造的に失敗を排除する仕組み**へとアーキテクチャを再設計する。
