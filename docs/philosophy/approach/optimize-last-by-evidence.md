# 最適化は計測に基づく最終手段とする（Optimize Last, by Evidence）

性能の最適化は、積極的に行う行為ではなく、**根拠ある計測値が揃い、そのボトルネックを解消しない限り成果物が解くべき課題を解けなくなった場合に限って行う最終手段**である。

最適化は、コードの可読性、責務境界の明快さ、変更容易性と引き換えに性能を得る行為である。
計測に基づかない最適化は、支配的でない箇所に複雑性を持ち込み、その代償を将来の保守者へ負わせる。

## 最適化に着手する条件

最適化への着手は、以下の条件がすべて満たされた場合に限る。

* **性能要件の定義**：応答時間、スループット、資源使用量などの性能要件が、[非機能要件として不変条件の形で定義](../system-design/requirements-and-invariants.md)されている。
* **計測による違反の実証**：再現可能な計測によって、当該不変条件が破られていることが実証されている。
* **ボトルネックの特定**：計測結果から要件違反の支配的要因が特定されており、その解消なしには要件を満たせない。

「遅いと感じる」「将来負荷が増えるかもしれない」という推測は着手の根拠とならない。
計測値は性能に対する[判定器（オラクル）](oracle-first.md)であり、判定器を欠いた最適化は、改善したことも退行しなかったことも証明できない。

## 見直しの順序

性能要件の違反に対しては、実装の局所的な最適化よりも、上位の層から原因を疑う。
上位の層ほど一度の変更で得られる効果が大きく、局所的な最適化を積み重ねるよりも根本解決へ速く到達できる可能性が高いためである。

1. **非機能要件**：要求されている性能水準そのものが、成果物の解くべき課題に照らして妥当か。
2. **設計と責務境界**：不要な往復、重複した処理、不適切なデータの所有配置など、構造上の原因がないか。
3. **アルゴリズムとデータ構造**：計算量やデータアクセスの形が、要件の規模に適合しているか。
4. **局所的な実装**：上記の見直しを経てもなお残るボトルネックに限り、実装を最適化する。

性能問題は、多くの場合 [支配的要因](find-the-dominant.md) が設計や要件の層にあることを示す症状である。
症状が現れた実装箇所のみを修正しても、構造的要因は残り続ける。

## 要件の見直しは人間が判断する

非機能要件の見直しは要件そのものの変更であり、[人間が制御すべき対象](human-steers-ai-implements.md)に属する。

AI エージェントなどの自動化機構は、計測結果、ボトルネックの分析、要件を変更した場合と維持した場合の代替案を提示するところまでを担う。
自動化機構が独自の判断で性能要件を緩和し、それをもって問題の解決と報告してはならない。

## 最適化を行う場合の規律

最終手段として最適化を行う場合、以下の規律を遵守する。

* 改善前後の計測を再現可能な形で残し、要件の充足を判定する証拠とする。
* 最適化による複雑性を最小のコンポーネント内に局所化し、公開契約へ漏洩させない。
* コードから復元できない最適化の理由と前提となった計測を、[コメントとして記録](../practices/comments-explain-why.md)する。

前提となった計測条件が失われた場合、その最適化は維持すべき根拠を失う。
根拠を失った最適化は、[削除の規律](../system-design/deletion-and-deliberate-absence.md)に従い、より単純な実装へ戻すことを検討する。
