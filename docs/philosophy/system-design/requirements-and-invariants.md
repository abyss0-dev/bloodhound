# 要件と不変条件（Requirements and Invariants）

設計は、システムが維持すべき振る舞いおよび品質の定義から開始される。
機能要件は何を実行すべきかを規定し、非機能要件はセキュリティ、信頼性、整合性、性能、運用性といった品質特性を規定する。

すべての要件は、1つ以上の**不変条件（Invariant）**へ変換されなければならない。
不変条件とは、「システムの状態遷移や外部環境の変化にかかわらず、常に真であり続けなければならない論理的制約」を指す。
不変条件は、特定のファイル配置、ライブラリ、実装手法よりも長期にわたり存続する。

## 不変条件を起点とした設計

不変条件の特定後、それを保護する責任（Ownership）を特定のコンポーネントまたは責務境界へ割り当てる。
設計は、適正な実行パスが選択されるよう誘導し、不正状態を構造的に制約し、静的な強制が困難な領域には観測可能な境界を確立しなければならない。

設計プロセスでは、以下の4つの関心事を明確に区別する。

* **要件（Requirement）**：システムが実現し保護すべき振る舞いや品質。
* **不変条件（Invariant）**：要件を満たすために、常に真でなければならない条件。
* **設計（Design）**：不変条件を保護するために割り当てられた責任境界とメカニズム。
* **証拠（Evidence）**：設計が正しく機能していることを実証する観測結果。

テストやチェック機構は不変条件そのものではなく、検証証拠の1情報源に過ぎない。
要件および不変条件の定義を欠いたまま検証項目のみを増大させる行為は、システムの本質的要求ではなく、偶発的な実装構造を固定化させるリスクを伴う。

## 設計時の評価項目

設計の妥当性を評価するにあたり、以下の検証項目を満たすことを義務付ける。

* 保護対象となる機能要件および非機能要件が特定されているか。
* 要件の成立に必要な不変条件が定義されているか。
* 不変条件を保護する責任を持つコンポーネントまたは境界が単一に定まっているか。
* 違反の防止、局所化、または外部への露出が構造的に保証されているか。
* 不変条件の充足を証明する独立した証拠（Evidence）が確保されているか。
* 実装手段を代替した場合であっても、不変条件がそのまま維持されるか。

本検証順序の遵守により、不変条件の保証レベルを損なうことなく、実装の進化を可能とする。
