# 唯一の事実源（Single Source of Truth）

すべての宣言的事実は、唯一の権威ある所有者（Authoritative Owner）を持たなければならない。
これには、スキーマ定義、依存関係のバージョン、インフラ定義、デプロイ設定などが該当する。

これら事実をテストコードや補助スクリプト内に複製して固定化した場合、「第2の権威」が生じる。
複製されたデータは時間経過に伴い元の定義から乖離（ドリフト）し、単一の変更に対して複数箇所の同期編集を強制する。
その結果、整合性検証のための機構が、かえって不整合の原因となる。

## 設計ルール

検証手法の選定に先立ち、**唯一の事実源（Source of Truth）**を確定する。
他のコンポーネントはその事実源を直接参照するか、その実行結果を観測するものとし、期待値リストを並行して重複定義することを禁じる。

* **派生成果物（Derived Artifacts）**：機械的に自動生成され、いつでも破棄や再生成ができる複製は許容される。
* **手動管理のコピー**：手動で保守される複製は派生物ではなく、「競合する第2の権威」と判定し排除する。

## 所有権における意味論の包含

単一所有権の原則は、保存値のみならずその「意味論（Semantics）」に対しても適用される。
フォーマットやプロトコルを定義したサブシステムが、その構文、意味、ライフサイクルを最も正確に管理する。
したがって、権威ある事実源の解釈は、その所有サブシステムが提供するネイティブな実行および検証の機構に委譲されなければならない。

独自スクリプトによる解釈ルールの再実装は、元の事実源を参照している場合であっても、第2の意味論的権威を形成する。
独自の解釈器は仕様変更や境界条件への追従が困難であり、潜在的な仕様乖離の要因となる。

検証手法の選定では、以下の優先順位に従う。

1. 所有サブシステムの通常の実行パス
2. そのサブシステムが提供するネイティブな検証や計画のコマンド
3. アプリケーション境界における振る舞いテスト
4. 独自チェッカー（上記の方法では表現できないプロジェクト固有の知識を追加する場合にのみ限定）

## 設計時の評価項目

設計の妥当性を評価するにあたり、以下の検証項目を満たすことを義務付ける。

* 当該事実を所有する単一のファイルまたはサブシステムが特定されているか。
* 仕様変更時に、同一事実を複数箇所で同期修正する構造が排除されているか。
* 利用側コンポーネントが、権威ある定義を直接参照して適用しているか。
* 所有サブシステム自身が、自らの定義を解釈して強制しているか。
* 自動生成成果物が、リポジトリの元ソースと混同されずに分離されているか。
