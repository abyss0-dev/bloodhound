# review-pr-against-philosophy

変更に含まれる設計判断が `docs/philosophy/` の考え方で説明できるかを確認する。
規則への適合を判定するのではなく、判断の根拠が成立しているかを確かめる。

原則の内容はこの skill に書かない。
毎回 `docs/philosophy/` を読み、そこを唯一の拠り所とする。

## まっさらな文脈で実行する

レビューは、変更の作成や議論の経緯を含まないまっさらな文脈で行う。
作成時の意図や会話を知っていると、差分と説明文に書かれていない根拠を無意識に補ってしまい、根拠の欠落を見落とすためである。

* 変更を作成したセッションや、その会話を引き継いだセッションではレビューしない。
* そうしたセッションで依頼された場合は、会話を引き継がない新しいサブエージェントを起動し、PR 番号または対象ブランチだけを渡してレビューさせる。
* レビューに使う材料は、差分、PR の説明文、紐づく issue、リポジトリ内の文書に限る。

## 手順

1. **変更を集める。**
   PR 番号が与えられた場合は `gh pr view <番号>` と `gh pr diff <番号>` を使う。
   与えられない場合は、現在のブランチとデフォルトブランチの差分（`git diff <default>...HEAD`）を対象とする。
   説明文や紐づく issue があれば、それも読む。
   説明文は事実ではなく検証すべき主張として扱う。
   説明文にない設計判断が差分に含まれていないか、書かれた証拠が差分やテストから確認できるかを確かめる。
2. **`docs/philosophy/` を全文読む。**
   一部だけを読んで判断しない。
3. **変更の目的を一文で書く。**
   変更がどの要件を満たそうとしているかを確定させる。
   目的が読み取れない場合は、それ自体を報告する。
4. **主要な設計判断を取り出す。**
   新しい抽象や境界の導入、データや定義の複製、検査の追加や削除、最適化、可変状態の導入など、構造に影響する判断に絞る。
5. **判断ごとに、philosophy の考え方で説明できるかを確かめる。**
   要件 → 不変条件 → 信頼できる情報源 → 所有するメカニズム → 観測可能な結果・証拠 の連鎖を辿り、途切れている箇所を探す。

## 報告

結果は会話内に報告する。
PR へのコメント投稿は、明示的に指示された場合を除いて行わない。

```markdown
## 変更の目的
（一文）

## 指摘
- **（説明できない判断 / 根拠の不足 / 検討の余地）** `パス:行`
  何が説明されていないか。どの考え方（`docs/philosophy/...` の文書と節）に照らしてそう言えるか。

## 作成者への質問
（差分だけでは判断できない点）

## 確認した範囲
（取り出した設計判断の一覧と、問題がなかったものはその旨）
```

指摘の種類は、このままマージした場合の帰結で選ぶ。

* **説明できない判断**：判断と要件のつながりが示されていない。
* **根拠の不足**：判断は妥当そうだが、計測、判定器、記録などの裏付けが欠けている。
* **検討の余地**：別の考え方を取ればより単純になる可能性がある。

指摘がなければ、ないと報告する。
指摘の数を揃えるために弱い指摘を足さない。

## 守ること

* 「〜に違反」とは書かず、「〜の考え方に照らすと、この点が説明されていない」と書く。
* 差分に根拠がある場合に限って指摘する。推測で欠陥を作らない。
* 文体、命名の好み、書き方の癖は指摘しない。
* 将来に備えた抽象化や一般化を求めない。
* 要件、特に非機能要件を変える変更は、人間の判断が必要な点として明示する。
* 承認、マージ、コードの修正は行わない。
